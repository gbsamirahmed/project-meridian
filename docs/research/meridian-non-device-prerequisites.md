## 7. Offline storage and recovery requirements

The [hardened desktop design](../../scripts/atlas/portable-spike/HARDENING.md) and [shared/window findings](atlas-portability-handoff.md#6-raster-and-offline-portability) demonstrate bounded NTFS process-interruption behaviour, not mobile or general power-loss durability. Native app storage and a browser origin are materially different custody environments.

| Platform / D source | Established API distinction | Required target proof / unresolved guarantee |
|---|---|---|
| Android [app-specific storage](https://developer.android.com/training/data-storage/app-specific) | Persistent internal files and cache are distinct; low storage may remove cache, uninstall removes app-specific files, removable external storage can become unavailable | Put deliberately retained packages in an appropriate persistent location with explicit quota/free-space policy. Verify interrupted writes, restart, user removal, low-space handling and snapshot lifetime. [AtomicFile](https://developer.android.com/reference/android/util/AtomicFile) is a single-file helper and supplies **no locking**, not a multi-member package transaction |
| iOS [file-system guidance](https://developer.apple.com/documentation/foundation/using-the-file-system-effectively) | Application Support is the documented location for internal support files; caches/tmp are not dependable retention. Backup eligibility/exclusion is a separate decision | Container paths, file-protection/locked-device access, space/backup policy, replacement and restart must be tested on actual supported versions; no Android/NTFS path transplant or promised universal atomic package commit |
| Browser [Storage Standard](https://storage.spec.whatwg.org/), [WebKit policy](https://webkit.org/blog/14403/updates-to-storage-policy/) | Origin storage has quota/usage estimates and persistence requests; grants/limits depend on browser/context. User clearing remains possible | Do not promise automatic persistence or identical WebView/full-browser quotas. Test denied persistence, eviction, private mode, origin change, quota exhaustion and relaunch; disclose unavailable capabilities |
| Browser IndexedDB / [OPFS documentation](https://developer.mozilla.org/en-US/docs/Web/API/File_System_API/Origin_private_file_system) | IndexedDB provides structured transactional storage; OPFS provides origin-private files and worker access facilities, subject to storage management | An IndexedDB transaction is not a transaction across arbitrary OPFS files, cache and native kernels. Define candidate verification and small selection commit; prove lifetime/locking and compatibility under worker/process interruption |

Shared behavioural obligations, **not a selected storage implementation**:

- **Cache:** disposable acceleration; eviction is expected and never implies scientific absence.
- **Downloaded resource:** staged bytes; receipt/completion of transport does not establish scientific readiness.
- **Verified installed package:** bounded member/schema/profile/integrity and scientific dependency closure passed; retain last compatible ready package during replacement.
- **Selected scientific generation:** exact requested publication available in a compatible installed package; separate from installation identity, no silent pin fallback.
- **Immutable open snapshot:** selected verified contents cannot change under ongoing queries; bounded capture/owned handles/revalidation policy must be justified and tested on the target. One-time hashes do not protect future arbitrary mutation.

Ready publication and selection have explicit commit boundaries; interrupted candidates never become ready merely on restart. User deletion clears affected selection without silently substituting another generation; already-open snapshots obey the documented lease policy and eventually release resources. Space reservation is planning, not guaranteed available bytes under concurrent use. Preserve user routes/waypoints separately from removable geographical packages. Corruption, missing resources and incompatible versions are availability/integrity failures, not successful empty queries.

Downloads need bounded retry/resume identity, cancellation and failure diagnostics; no background continuation promise. Android's [long-running WorkManager guidance](https://developer.android.com/develop/background-work/background-tasks/persistent/how-to/long-running) describes Android 16 job-quota constraints. Apple [background URLSession](https://developer.apple.com/documentation/foundation/urlsessionconfiguration/background%28withidentifier%3A%29) can transfer outside the process, but user force-quit cancels transfers and prevents automatic relaunch. Browser/background-worker availability is different again. These are inputs to host-specific tests, not reasons to implement a downloader now.

Integrity seals are **not publisher authenticity**. Before external packages, choose a justified trusted-origin/update/key policy for that actual distribution route, and separately audit runtime dependencies. No keys, signatures, remote delivery or production trust mechanism are introduced. Process-termination tests do not establish power-loss durability or hostile multi-writer security; record the precise claim and unsupported cases.
